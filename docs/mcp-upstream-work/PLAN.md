## 必须优先解决的技术问题

### 工具链与 MCP 依赖

主线实际采用分平台工具链：多数路径 Rust 1.75，macOS Rust 1.81，Windows x86 Sciter 使用专门的历史 nightly。Flutter 通常为 3.24.5，Windows ARM64 使用 3.44.9；桥接生成也存在两套 Flutter 版本。按各现有构建配方验证，而不是统一升级工具链。

原实现的 `rmcp 3.3.0` 要求 Rust 1.88，使用 2024 edition。已下载检查的 `rmcp 0.1.0`、`0.1.5`、`0.2.0` 也采用 2024 edition，因此不能把“换一个旧版 SDK”视作已解决方案。[官方 SDK 清单](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.3.0/Cargo.toml)

2026-09-18 用户已确认自行实现 MCP 协议适配层，底层复用主线已有的 Hyper/Tokio/Serde 兼容组合，SDK 选型到此结束，见 [D09 决策](DECISIONS.md) 和 [研究证据](MCP-SDK-RESEARCH.md)。协议处理集中在独立功能模块，接入现有运行时；HTTP 解析和 JSON 编解码由成熟库承担。随后明确支持的协议版本及能力声明，完成工作区依赖/feature 审计和官方客户端互操作。禁止以手写 HTTP 解析器、复制整套 SDK、全局升级 Rust 或大范围重锁依赖换取短期通过。这是全量实现的组成部分，不是一个单独的原型交付。

嵌入式方案作为优先方向：独立伴随进程会增加各平台打包和移动端部署负担，不直接用它绕过问题。依赖审计同时覆盖 feature 开启和关闭的解析、锁文件格式、传递依赖及目标平台要求。

### 移动端服务必须实际可用

Android/iOS 与桌面共享协议、会话权限和工具语义，但服务启停、凭据路径、后台状态由平台生命周期接入。协议接入时就按所支持版本验证移动端的发现/初始化、工具列举及调用，并在同一 PR 完成所有适用功能，不能到收尾阶段才尝试移动构建。

iOS 普通应用进入后台后会被系统挂起，额外后台执行时间也有限。因此初始设计以应用前台服务为基础：进入后台时撤销输入权限、取消排队写操作并释放按键；恢复后刷新状态并重新授权。实际可用的客户端组合、本机跨应用访问、iPad 多窗口以及 USB 访问需要分别验证。USB 测试通过不能算作本机 AI 客户端体验已经通过。[Apple 生命周期约束](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)

Android 同样先验证前后台、锁屏、进程终止和网络切换。若需要持续后台服务，应单独证明它符合 Android 服务生命周期与用户可见要求，而不是借用现有远控服务无条件保活。

每项能力必须区分控制端平台限制、被控端能力、运行时权限与尚未实现。只有平台或原版协议确实不提供对应机制时，才可报告 unsupported，并记录依据；不能用 unsupported 占位掩盖某个平台未完成的实现。例如手机没有桌面 OS 窗口布局操作，与手机上的 MCP 服务能够操作远端 Windows 虚拟显示器，是不同问题。移动端文件权限/沙盒、录制保存、终端与隧道都需要完整设计和验证。

默认要求本地授权后才能由 AI 写入；新建连接和附着已有连接采用一致原则。参考分支“AI 新建会话后自动获得控制”的策略不直接沿用。远端认证与本地控制授权仍是两个独立条件。

## 实现约束

1. 沿用新主线 `AGENTS.md`：客户端配置键位于 `base::config::keys`；客户端新增代码归本仓库，避免修改共享 `hbb_common` 子模块。
2. 新逻辑放在功能模块，共享会话、输入、视频代码仅添加必要的受 feature 控制的调用。关闭功能时保留原实现路径，避免为了复用而改变通用 trait、函数签名或让所有调用方填新占位参数。
3. 使用现有 Tokio 运行时，避免嵌套运行时、跨 await 持锁和阻塞式等待；截图编码等耗时工作限制并发并离开 UI/网络线程。
4. 复用现有会话与认证状态，按会话和视图标识定位，避免仅凭远端 ID 操作错误窗口。MCP 客户端权限独立且不可相互继承。
5. 在真正发送输入的位置再次验证控制代次，覆盖已排队请求、重连、超时、断开以及人类接管的竞争条件。人工输入没有活动 MCP 控制时仍走原路径。
6. 截图先审查现有取帧/截图入口，覆盖软件渲染、硬件解码和 Windows GPU texture 路径；避免对每帧无条件复制、全局关闭硬件加速或创建额外远端连接。现有人工截图的缓存和通知语义必须保留。
7. 依平台正确保存本地凭据：Windows 用户权限/ACL、Unix 文件权限、移动应用私有目录；不可直接移植原实现的 Unix-only 文件权限逻辑。
8. 服务默认关闭、绑定 loopback、验证认证以及 Host/Origin，限制请求大小和并发；撤销令牌时失效会话和控制权。遵循 [MCP Streamable HTTP 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。
9. Flutter 共享设置和状态组件供桌面与移动使用；Web 与 Sciter 的既有客户端构建保持可用，不能因引用新增桥接 API 而失败。暂不将浏览器或 Sciter 声称为已有 MCP 服务端实现。
10. 遵守主线 import、注释和本地化规则。生成文件使用主线桥接工具；新增文本按主线 key 流程处理，不顺带翻译或修整其他文本。每个提交保持可构建，并按贡献规范带 DCO sign-off。

## 工作顺序与交付门槛

当前优先推进三项：原版主线构建、Rust 1.75 协议实现路线与互操作、移动端尽早打通。三者可以并行：移动端先配置 SDK/runtime 并跑通 iOS 模拟器和 Android 构建，协议接口就绪即验证应用内服务启停、客户端连接和生命周期。静态接入审查及 CI 扩展是配套工作，不能替代移动端实际构建/运行，也不应把移动验证推迟到全部业务实现完成。

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| A：基线和依赖路线 | 原版主线构建；Rust 1.75 依赖验证；用可用设备及模拟器尽早验证五平台服务生命周期/客户端接入；固定完整能力映射 | 依赖路线有实际证据，平台边界注明依据与验证状态，全部功能组已有实现与测试安排 |
| B：全量实现 | 依次完成会话/授权/输入、显示/设置、文件/剪贴板、终端/隧道、录制/聊天、安全动作；五平台同步接入 | 67 项参考能力均有新实现或有依据的平台边界，全部纳入同一 PR |
| C：覆盖验证 | 在现有资源上完成功能组合、控制权竞争、认证/2FA、断线恢复、移动生命周期、各架构与旧系统、默认路径回归；最后汇总缺资源的测试 | 实现、构建、运行状态分别记录；能执行的测试有结果，缺资源项有明确的社区补测步骤，已发现缺陷继续修复 |
| D：单个完整 PR | 小而自洽的提交、DCO、架构说明、测试证据、安装包、逐文件回归面检查和维护者反馈 | 全部约定功能完成、现有资源可执行的验证达标、已知问题处理后标记 ready；同时披露社区待补测试，由维护者判断是否需要作为合并条件 |

可以在实现过程中尽早把同一个 PR 标为 Draft 供维护者反馈，但最终交付与 ready 门槛始终是完整 MCP 集成，不能以提交 Draft 或部分核心流程替代完成。不存在把上表任一功能组安排到后续 PR 的计划。合并时间取决于上游审查；完成依赖和全量差异评估后给实现时间估算，主要不确定性是 Rust 1.75 依赖、移动端接入和跨平台原生能力。

测试资源按可获得性安排，不追求在提交前穷尽所有终端组合。确实缺设备的运行测试标为“待社区补测”，不标为通过、不适用或未实现。最后为每个缺口准备构建版本/提交、系统与架构要求、复现步骤、预期结果、日志收集方式及已有替代证据，交给用户发布求助；当前不代用户向社区发送消息。

在基础接口完成、提交 PR 前和反馈修订完成时同步最新 master；出现冲突只处理相关改动。保留一个面向上游的分支，不持续搬运参考分支的新功能。

## 构建与运行矩阵

每个平台记录三种状态：未编译 MCP、编译 MCP 但运行关闭、MCP 启用。桌面/移动新增功能与旧版客户端回归分开记录；构建成功不能代替运行测试。

| 消费者 | 构建目标 | 运行验证 |
| --- | --- | --- |
| Windows Flutter | x86_64、aarch64，沿用主线工具链/Flutter | Windows 10/11、Windows 7 x64；ARM64 另测；权限/多窗口/软硬解 |
| macOS Flutter | x86_64、aarch64，Rust 1.81 | 当前 ARM64 Mac 主测；Intel 和旧部署目标补测 |
| Linux Flutter | x86_64、aarch64 | X11 和 Wayland，桌面会话、窗口生命周期和显示布局 |
| Android Flutter | aarch64、armv7、x86_64；按主线实际支持列表 | 已有手机优先验收服务与后台/网络行为，接入后核实 ABI；模拟器补版本和架构 |
| iOS Flutter | 分别构建 aarch64 真机与 aarch64 模拟器目标 | 模拟器覆盖完整适用功能及生命周期回调；真机后台/资源/网络/签名等运行证据待借机或外部测试补齐 |
| Windows/Linux Sciter | Windows i686、Linux x86_64/armv7 等现有配方 | 默认功能与构建回归，32 位大小和依赖解析 |
| Web/F-Droid/发行包 | 按主线配方、特性与权限 | Web 桥接回归、Android/F-Droid 配方、安装包/沙盒行为 |

上游普通 PR 工作流不会运行全部发行路径：iOS、部分 Linux ARM64/Sciter/包格式只在其他条件下执行。补充验证使用 fork 的测试工作流，显式选择目标和构建参数，避免把“绿色 PR CI”当作完整覆盖。[当前主线构建工作流](https://github.com/rustdesk/rustdesk/blob/5278fcab685723099e9950d56cb605807db5aa2a/.github/workflows/flutter-build.yml)

本机 ARM64 来宾优先用 UTM 虚拟化，Windows/Linux x64 与 Win7 使用按需模拟环境，原生 x64/GPU/双屏集中到用户可提供的 Windows 真机。每次只开一台 VM 或一个模拟器，大规模构建交给 CI。记录硬件虚拟化、跨架构模拟和真机的差别，不将模拟性能用作产品性能结论。

iOS 当前工程直接链接真机 Rust 静态库，需补独立模拟器目标及原生依赖。完整实现与 PR 提交可以在没有 iPhone 的条件下继续；对后台挂起、内存回收、设备网络、签名安装等无法由模拟器证明的项目，保留明确的真机验证缺口，最后交由用户请求社区补测。模拟器通过不等于真机全部验收通过，也不据此删除 iOS 功能。

控制端矩阵与被控端矩阵分别验证：例如 Windows 上运行 MCP 去控制 Linux，以及 Mac 上运行 MCP 去控制 Windows，是两条不同路径。先用共享的原版 Windows/Linux 被控节点覆盖每个控制端，再补高风险组合，无需对所有 OS 版本作笛卡尔积。

测试清单包括：人工接管时仍有输入排队、按键按下后断连、令牌轮换、多客户端争用、远端权限撤销、认证失败/确认、显示器切换/负坐标/DPI、非 ASCII 文本、窗口关闭/重连、移动挂起/恢复、关闭 MCP 后正常手动远控。进一步覆盖：文件重名/断传/续传/取消与沙盒路径授权，原生文件剪贴板，终端二进制输出/关闭/重连，隧道隔离认证/端口释放/半连接，录制文件完成/权限撤销，聊天游标/去重，真实 2FA 成功/失败，提权成功/拒绝，隐私/输入屏蔽恢复，以及虚拟显示器创建/移除。参考分支历史未测项本次全部重新入账，现有资源能测的先完成，确实缺资源的留在社区补测清单。

- 本机：ARM64 Mac、24 GiB 内存、约 598 GiB 可用空间；Xcode 27.0；Rust 1.75/1.81 已安装；已有 Flutter 3.24.5 和 vcpkg 缓存。当前 shell 未默认找到 Rust，后续使用显式工具链路径。
